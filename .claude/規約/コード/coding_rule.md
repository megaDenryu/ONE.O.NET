# コーディング憲法

本憲法はこのリポジトリの C# に適用される設計原則である。

## 第0条：型安全性の最優先

1. **`any` は禁止。** `unknown`（TS）/ 動的型（Python）/ `object`（C#）は外部境界（API応答、JSON parse等）での受け取りにのみ許容し、即座に型ガードで絞り込むこと。型が合わないときに `as` キャストで逃げるのは設計の歪みの兆候であり、型を通すために設計自体を見直す。
2. **作ろうとしているものに忠実な型を書く。** コンパイルを通すためだけの形式的な型付けは禁止。型が実際に作ろうとしているドメインの構造を忠実に反映しているかを常に問うこと。
3. **条件分岐は型システムで表現する。** if/switchによるランタイム分岐よりも、判別共用体（TS: Discriminated Union / Python: Literal + Pydantic tagged union / C#: `union` + `switch` 式）やポリモーフィズムで分岐をコンパイル時に保証せよ。特に状態管理において、「不可能な状態」を型で排除し、状態遷移の網羅性をexhaustive checkで保証すること。
4. **外部境界はDTOで閉じる。** JSON、API、WebSocket、ファイル、LLM応答などの外部入力は、境界でDTO・型ガード・Pydantic等により検証済みの構造へ変換する。`Record<string, unknown>` や `dict[str, object]`、C# の `Dictionary<string, object>` や `JsonElement` のような非構造化データをアプリ内部へ流してはならない。
5. **入力・出力・エラーは名前付き型として最小単位で定義する。** 判別共用体の各バリアントを巨大な union へ辞書リテラルで直書きし続けてはならない。命令、イベント、応答、エラーなどの意味単位ごとに名前付き型・DTO・クラスを定義し、呼び出し側は `Extract<巨大Union, ...>` の多用ではなく、その最小単位の型を直接受け取る。
6. **Result型で成功と失敗を表現する。** 成功・検証失敗・内部エラー・未検出などの分岐を、`Record<string, unknown>` や手書き辞書で返してはならない。成功時だけ存在する値、失敗時だけ存在する理由を判別共用体で分離し、不可能な組み合わせを型で排除する。
7. **DTOは変換と検証の責務を凝集する。** `type` と裸関数を散在させ、入力取得・検証・変換・シリアライズの所在を分散させてはならない。意味のあるデータ単位はDTOまたは値オブジェクトとしてまとめ、境界で何を受け入れ、何を拒否するかをその近くに置く。
8. **別の意味を持つ入力を既存の命令やDTOに便乗させない。** 形が似ていても意味が違うなら専用の命令・イベント・DTOを定義する。既存仕様に別構造を混ぜ込むことは、型安全性と検証責務を崩す設計負債である。
9. **必須入力の欠落を暗黙の既定値で補わない。** 欠落時に値を補う設計は、仕様上「省略可能で、省略時の意味が明確」と文書化されている場合に限る。操作命令や状態変更入力で必須値が欠けた場合は、境界の検証失敗として扱う。
10. **境界検証は存在確認だけで終わらせない。** 数値範囲、文字列の空禁止、列挙値、余計なフィールド、配列長、ネスト構造など、ドメイン上の制約を境界で検証する。Python側DTOとTypeScript側DTOのように同じ仕様を別言語で扱う場合、必須項目・範囲・エラー条件を揃える。

## 第1条：設計思想 — FP/OOPハイブリッド + DDD

1. **DDDの集約パターンを基本とする。** ドメインの境界を集約で定義し、集約内の整合性を保証する。
2. **FPとOOPを関心に応じて使い分ける。** 排反ではなく、同じドメイン内で組み合わせる。
   - **FP（純粋関数）を使う場面:** 状態遷移ロジック（Reducer）、データ変換、派生値の計算、View構築
   - **OOP（クラス）を使う場面:** ライフサイクル管理（リソースの獲得と解放）、外部接続の保持（WebSocket、タイマー等）、複数の購読やイベントハンドラの管理
3. **`this`なしで書ける判定・変換・フォーマットがメソッド内に埋もれていたら、名前付き関数への抽出を検討する。** ただし以下の場合はクラスメソッドのままが適切であり、何でも純粋関数にすればよいわけではない。
   - **「誰が」やるかにドメイン的意味がある場合。** `キャラクター.攻撃する(対象)` を `攻撃ダメージを計算する(攻撃者, 対象)` にするとユビキタス言語が消える。
   - **処理がオブジェクトの文脈（複数の私的状態や副作用の連鎖）に強く依存する場合。** 引数に分解すると呼び出し側が内部構造を知る必要が生まれ、凝集度が下がる。
   - 抽出した純粋関数は、**データ変換・判定・検証パイプライン**（入力と出力が明確で、状態を参照するだけ）に特に向いている。判定のルールチェーンは各ルールを `(入力) => 結果 | null` にして `??` で繋ぐと宣言的になる。
   - 抽出の目安: 関数に名前をつけることで**メソッド本体の可読性が上がるか**。上がらないなら無理に抽出しない。
4. **不変性を基本とする。** データは変更せず新しい値を返すことを基本とする（第3条の`with*()`パターン）。可変状態が必要な場合は局所化し、理由を明記する。
5. **Composition over Inheritance。** ドメイン層でのクラス継承は禁止し、インターフェースと移譲パターンを使用する。UIコンポーネント層での継承は許容する。

## 第2条：依存性注入（DI）とコンポジションルート

1. クラスの依存は**コンストラクタ注入**で受け取る。
2. 具象クラスへの直接依存は避け、**インターフェースまたは抽象型**に依存する。
3. サービスロケータパターンやグローバルシングルトンは禁止。共有状態が必要な場合は、明示的にコンストラクタで注入する。
4. **依存の配線はコンポジションルート1箇所に集約する。** アプリ起動時のファクトリ（例: `AppFactory.create()`）が唯一の組み立て地点であり、サービス・Router・handlerが自分の依存を内部でインスタンス化してはならない。`DataDir._()`等のグローバル状態へのアクセスもコンポジションルートに限定し、消費側には解決済みの値（Pathインスタンス、サービスオブジェクト等）をコンストラクタや関数引数で渡す。

## 第3条：値オブジェクトと型変換

1. **値オブジェクトはクラスとして実装する。** privateコンストラクタ + staticファクトリメソッドで生成時にバリデーションを保証し、`with*()`メソッドで不変な変換を提供する。
2. **型変換はオブジェクト自身のメソッドとして定義する。** `self.toOther()` 形式で変換を書き、メソッドチェーンを可能にする（例: `画面座標点.to描画座標点(基準座標)`）。
3. **プリミティブ執着の禁止。** ドメインの境界を超えてプリミティブ型（number, string等）を受け渡さない。`Px長さ`、`付箋ID` のような値オブジェクトで包む。

## 第4条：暗黙より明示

1. **コードを読めば動作が分かるように書く。** 自動追跡、暗黙的な依存解決、フレームワークの裏側の挙動に頼らず、依存関係・データフロー・副作用の発生箇所が明示的にコード上に現れるようにする。
2. **手続き的ループよりも宣言的メソッドを優先する。** `map`, `filter`, `reduce` 等を使い、処理の意図を明確にする。
3. **副作用は局所化する。** 状態変更は関数の末端に集約し、純粋な計算と副作用のある操作を明確に分離する。

## 第5条：コメント方針（2026-07-06 改訂）

1. **コードから読み取れない情報を記録する。** 設計判断の理由、代替案を選ばなかった理由、ドメイン上の制約、地雷、外部への参照など。命名・構造・型で伝えられることは書かない。
2. **What/Howはコード自体で表現する。** howコメントが必要と感じたらまずコードの可読性改善を検討する。複雑なアルゴリズムや非自明な制約にはHowを許容するが、要点のみ簡潔に書く。
3. **`Why:` プレフィックスは禁止。** 日本語として不自然であり、実際は「なぜ」以外(不変条件・注意喚起・地雷警告・過去バグ経緯・参照)が混在してタグの意味が形骸化していた。文章そのものが因果構造(「〜のため、〜する」「〜だと〜になるので〜」)で理由を語れば札は不要。
4. **プレフィックスは以下の3種類のみ許容する。** スキャン時に読み手が本文を全部読まなくても察知すべき情報にだけ札を貼る:
    - `注意:` — 触ると壊れる不変条件・地雷・順序依存(例: 「この2条件遮断を外すと無限ループが成立する」)
    - `前提:` — このコードが成立するために外部で保証されている条件(呼び出し順、呼び出し文脈、状態不変条件)
    - `参照:` — 他ファイル・ドキュメント・開発スレッドを見ないと分からない設計判断への案内
5. **禁止するコメントパターン。**
    - **変更履歴コメント**: 「旧実装は〜だった」「YYYY-MM-DDに〜を修正」「コミット○○で追加」等。git blame で足りる。同一バグの再発防止として現状の構造を保つ必要があるなら `注意:` で「壊すと何が起きるか」を書く(過去との差分ではなく将来への警告として)。
    - **書き手・経緯**: 「Claude/Codex/Copilot が書いた」「AIによる実装」等。出所は不要。
    - **TODO/FIXME**: Issue化する。コード内には残さない。
6. **翻訳コメントは第5条の削除対象外。** 英語のライブラリAPI (`shutil.copy2` 等) や英語の制御構文に付された日本語コメントは、日本語話者にとって英語コードが必ずしも自明でないための「翻訳」として機能する(第7条-3 と整合)。

### コメント本文の書き方

1. **句読点や段落の切れ目以外で改行しない。** エディタの折り返しに任せる。「〜のため、\n〜する」のような不自然な改行を作らない。
2. **プロパティ・引数・変数のコメントはインライン**（右横に `//` で1行）で書く。プロパティが並んでいる中に何行もの上部コメントを挟むと視覚的な塊が壊れ、宣言の一覧性が消える。長くて1行に収まらないなら、そのフィールドは名前 or 型が悪いことを示唆しているのでコード側を改善する。
3. **タグの数式的な多用を避ける**（`注意:` を2連続で貼らない等）。段落の切れ目で自然に読ませる。

### 補足: コメントが長くなったらコードを疑う

散文が5行以上になるなら設計自体に何か歪みがあるサインである。まず構造改善を検討する。それでも長い注意が必要なら、開発スレッドへリンクして本文は要点だけにする(`参照:` の出番)。

## 第6条：命名規則

1. **日本語の命名を積極的に使用する。** 特にドメイン層のクラス名、メソッド名、変数名において。
   - 例: `キャラクター表示モード`, `ダメージ計算結果`, `表示位置を更新する()`
2. 英語を使用する場合は、ドメインのユビキタス言語辞書に登録された用語を使用する。
3. 略語は原則禁止。フルスペルで書く。

## 第7条：スコープ外行動の禁止

1. **依頼されたタスクと無関係なフォーマット変更は禁止。** バグの混入リスクとレビューコストが増大する。
2. **依頼されたタスクと無関係なリファクタリングは禁止。** 必要と判断した場合は、ユーザーに承認を求めること。しかしリファクタリングをしないでどんどんコードを汚くすることはより犯罪である。必ず立ち止まること。
3. **既存の日本語コメントを無断で削除してはならない。** 第5条では「自明なコードにhowコメントは不要」という原則があるが、英語のライブラリAPI（`shutil.copy2`等）や英語の制御構文に付された日本語コメントは「翻訳コメント」としての役割を持つ。日本語話者にとって英語コードは必ずしも自明ではないため、これらのコメントは第5条の削除対象とならない。

## 第8条：絵文字使用の厳格な禁止（Emoji Ban）

1. **文字列（String）内での絵文字使用は絶対禁止。** Pythonのログ出力やElectronのランタイム間でエンコード/デコード処理がクラッシュする致命的なバグの原因となるため。
2. **UIテキストでの絵文字使用も絶対禁止。** OneONet/VoiroStudioにおけるスタイリッシュでシリアスなデザインテーマを著しく損ねるため（ダサいため）。
3. **見かけたら即座に削除（Kill）せよ。** 既存のコードを編集する際に文字列内に絵文字を発見した場合、別件のタスク中であっても躊躇なく削除または適切なテキスト記号等に置換すること。
4. ※コード上のコメント（// や #）内に状況を分かりやすく表現するための絵文字は許容されるが、文字列として評価される場所には絶対に混入させてはならない。
