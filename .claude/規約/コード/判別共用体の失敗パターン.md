# 判別共用体の失敗パターン

このファイルは、型や状態の分岐を新しく書く作業、またはフィールドを足す作業に適用する。

このファイルの例は Python で書かれている。C# では `union` と `switch` 式で同じ設計を書く(`csharp_coding_rules.md` 第3条)。

## 判別共用体の設計失敗パターン(過去の Claude が繰り返した反省)

このプロジェクトのコードは全て Claude が書いてきた。コーディング憲法 (`coding_rule.md`) 第0条-3 および Python 憲法 第4条 は判別共用体の使用を義務付けているが、過去の Claude はこのルールを守れないケースを何度も繰り返している。以下は具体的な失敗パターンと、それを避けるためのチェックリスト。

### 失敗パターン: 「tagged flat class」を判別共用体と誤認する

```python
# ❌ 悪い例: ルール違反ではないが判別共用体の精神を満たさない
class 発話完了判定結果(BaseModel):
    kind: Literal["発話完了", "発話途中", "ノイズのみ"]
    理由: str
    整形済みテキスト: str | None = None  # 発話完了時のみ意味がある
    ノイズ混じり: bool = False              # 発話完了/途中のみ意味がある
    除去されたノイズ: list[str] = []        # 発話完了/途中/ノイズのみ すべてで意味がある
```

このクラスは `kind` という Literal を持つので**見た目には**判別共用体に見える。だが:

- `発話完了判定結果(kind="発話途中", 整形済みテキスト="あ")` が型チェック通過する(意味的に不正な状態が表現可能)
- 消費側は `if 結果.kind == "発話完了":` という文字列比較でしか分岐できず、**新しい kind を追加しても型チェッカーは何も言わない**(exhaustive check が効かない)
- フィールドを追加するたびに「このフィールドはどの kind に属するか」をコメントと運用ルールで表現するしかなく、時間とともに腐敗する

```python
# ✅ 良い例: 本物の判別共用体
class 発話完了(BaseModel):
    kind: Literal["発話完了"] = "発話完了"
    理由: str
    整形結果: 整形状態   # ここでしか存在しない
    ノイズ混じり: bool = False
    除去されたノイズ: list[str] = []

class 発話途中(BaseModel):
    kind: Literal["発話途中"] = "発話途中"
    理由: str
    ノイズ混じり: bool = False
    除去されたノイズ: list[str] = []

class ノイズのみ(BaseModel):
    kind: Literal["ノイズのみ"] = "ノイズのみ"
    理由: str
    除去されたノイズ: list[str] = []

発話完了判定結果 = 発話完了 | 発話途中 | ノイズのみ
```

消費側は `match` で網羅的に分岐でき、各 kind が持てるフィールドが型で保証される。不可能な状態が表現できない。

### なぜ Claude はこの失敗を繰り返すのか

1. **`kind: Literal[...]` があれば判別共用体だと誤認する**。本質は「kind 値ごとにフィールドが分離されていること」であって、`kind` フィールドの存在ではない
2. **差分最小化バイアス**: 既存クラスに `str | None` を1行足す方が楽なので、クラス分割を避ける。結果として毎回1ミリずつ型が腐敗する
3. **フィールド追加時に「どの kind に属するか」を問わない**: 特定の kind にだけ属するフィールドを追加したら、その時点で「このクラスは単一では表現できない」のサイン。運用ルールで済ませるのは未来の腐敗を招く
4. **exhaustive check が効かないのでフィードバックがない**: フラットクラス + `if kind ==` 方式は、新しい kind を追加しても型チェッカーが何も言わない。間違いが表面化しない
5. **過去の Claude の失敗が未来の Claude の「慣習」になる**: このプロジェクトのコードは全部 Claude が書いた。過去の Claude が書いた `str | None` パターンを現在の Claude が「プロジェクトの既存慣習」として真似する負のループが発生する
6. **「動けばいい」の暗黙バイアス**: 型設計を後回しにすると動作には影響しないので軽視されやすい。しかし後から直すコストのほうが初期投資より遥かに大きい

### チェックリスト(新しいフィールドを追加する時・新しい型を書く時)

フィールドを追加する前、または新しい型を定義する前に以下を声に出して問え。問わずに `str | None` や `bool = False` を足そうとしたら立ち止まれ。

1. **「このフィールドは全ての kind に属するか? 特定の kind にだけ属するか?」**
   - 「特定の kind にだけ」と答えたなら、そのクラスは単一クラスでは表現できない。分割しろ
2. **「このクラスを `(kind=X, field=Y)` の形で構築したとき、意味的に不正な組み合わせが作れるか?」**
   - 作れるなら不可能な状態が表現可能。型で排除すべき
3. **「消費側は `if 結果.kind == "..."` で分岐するか、`match 結果:` で分岐するか?」**
   - 前者なら判別共用体ではなく tagged flat class。後者に書き換えろ
4. **「新しい kind を追加したとき、既存の消費側コードは型エラーで網羅漏れを教えてくれるか?」**
   - 教えてくれないなら exhaustive check が効いていない = 判別共用体が機能していない
5. **「`str | None` / `T | None` を書こうとしている。それは『このフィールドは時々ある』のフラグか?」**
   - そうなら判別共用体で「あるケース」「ないケース」を分離すべきサイン
6. **「既存のコードに似たパターンがあるから真似する」と思った時、そのパターンは憲法に照らして正しいか?**
   - 過去の Claude が書いたコードを無批判にコピーしない。憲法のほうが上位
